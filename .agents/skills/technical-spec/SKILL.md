# 技术方案

以用户已确认的需求为范围，遵循仓库 `AGENTS.md` 中的方案结构、架构图和数据库变更要求。先核对当前实现和已有约束，再提出具体设计；事实、建议和未决事项分别表述。

## 从现状到方案

1. 从实际产品入口追踪到相关界面、接口、服务、存储和执行边界，读取必要的调用方与原始定义。列出本次需要保留的现有行为；无法核实的事实标明证据缺口。
2. 按本次需求走通用户路径：入口、选择或输入、系统响应、最终结果。结合已有产品方案或原型检查入口与状态；不把示例数据或尚未确定的交互写成已实现事实。
3. 对每项设计判断现有结构是否足够，优先复用或扩展。确需新增接口、状态、字段或流程时，说明现有能力缺少什么，以及新增如何解决；不要因历史问题扩展无关范围。
4. 按仓库要求调研相关 Harness 或开源方案，针对当前约束说明适用性和取舍；涉及现有代码变更时，用真实原文和必要的最小 diff 表达。

## 写清调用与状态

- 对涉及多个参与方或多个接口的流程，先写一个具体的端到端示例，再选择时序图或文字表达调用顺序。标明入口、调用方、输入来源、响应去向，以及按需并行或等待的关系；图只有在降低理解成本时才使用。
- 对拟议接口区分复用、扩展、新增或移除，并核对请求、响应与调用流程一致；关键字段说明来源、必填性和语义。覆盖本次需求中实际相关的取消、失败或恢复路径。
- 先呈现读者理解细节所需的关键流程，再介绍字段、限制和生命周期；术语与图中容易误解的符号在首次出现处解释。避免对同一完整流程用图和文字重复叙述。

## 交付前自查

- 从产品入口逐条对照方案与原型，确认现有行为、主要选择及其结果没有遗漏，数据能从上一步传到下一步。
- 核对时序图、接口表、字段定义、数据库 DDL、迁移、异常处理和验收是否相互一致；数据库与进程相关要求按 `AGENTS.md` 检查。
- 从不了解本次讨论的读者视角检查：现在怎样工作、为什么要改、具体怎样工作、哪些保持不变、如何验收。对无法验证的内容明确标注，避免把计划中的检查写成已通过。
- 方案任务只修改用户要求的方案及其直接配套材料；不顺带实施功能或发布外部内容。
