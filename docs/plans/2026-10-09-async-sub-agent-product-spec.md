# 后台异步子 Agent 产品方案

状态：功能已实现并通过自动化与浏览器验收（2026-10-12）。详细结果见[技术方案验收记录](./2026-10-09-async-sub-agent-technical-spec.md#7-实施验收记录2026-10-12)。

目标：父 Agent 委派子任务后可以继续独立工作；子任务完成后自动交付结果，父 Agent 据此继续推进并统一汇总。首期覆盖 Web 会话中同一个父任务内的异步协作。

本文定义用户体验、任务生命周期、功能边界和验收标准。工具接口、事件协议、调度方式及存储设计在技术方案中确定。

## 实施前基线（971b2b6）

当前 Web 会话已提供子 Agent 能力：

- 父 Agent 可以委派自足的子任务。子 Agent 使用独立上下文，沿用同一项目、模型及权限边界。
- 同一批次内多个子 Agent 可以并行运行。父 Agent 等待整批调用结束后才能继续下一步。
- 子任务的执行过程可以在现有子 Run 抽屉中查看，审批沿用会话中的确认入口。
- 子任务结束后向父 Agent 返回最终回答，并记录自己的结果、执行记录和用量。
- 主任务已支持浏览器断线后继续执行；关闭页面或切换会话不会自动停止服务端任务。
- 用户可以向运行中的父任务追加消息，父 Agent 在后续模型步骤处理。

## 存在的问题

父 Agent 委派后需要等待子任务结束。在子任务独立调查期间，父 Agent 无法继续检查其他内容、整合已获得的信息或处理下一步工作。

父 Agent 等待整批子任务时，用户已经提交的追加消息也需要等待批次结束才能被处理。多个子任务耗时不同时，先完成的结果无法提前供父 Agent 推进后续工作。

这些限制来自当前真实委派链路。异步化带来的耗时、任务质量和 token 成本变化仍需对照验证。

## 目标体验

典型任务：

> 用户要求调查某个页面的数据展示问题。父 Agent 让子 Agent 检查接口返回和字段含义，同时自己检查前端的数据映射。子 Agent 完成后，父 Agent 结合两边证据给出结论。

预期过程：

1. 父 Agent 创建“检查接口字段”子任务，用户看到该子任务开始执行。
2. 父 Agent 继续检查前端代码，子任务同时推进。
3. 子任务结果准备好后交给父 Agent，父 Agent 在当前步骤结束后处理。
4. 父 Agent 完成必要核对，给出包含两边证据的最终回答。

另一种情况是父 Agent 已完成自己的工作，正在等待子任务。此时应用显示“等待子任务”，子任务完成或用户追加消息后，父 Agent 可以继续推进。

## 具体改动

### 委派与并行执行

用户继续通过当前会话描述任务，由父 Agent 决定是否委派，不增加手动创建子任务的独立页面。

子任务成功启动后，父 Agent 获知任务已经开始，可以立即进入后续工作。启动成功与任务完成分开展示，启动确认不能被当作子任务结论。

父 Agent 必须给出明确的子任务目标、必要背景和预期交付。已有子 Agent 的独立上下文保留，父任务的新消息不会自动广播给所有子任务。

异步执行作为子任务的默认协作方式。父 Agent 需要结果才能继续时可以等待，不增加用户需要选择的“同步 / 异步”模式。

同一父任务最多同时保有 5 个活跃子任务；执行中、等待用户确认和正在停止的子任务均占用名额。达到上限时，新的委派返回“并发已满”，父 Agent 先处理已有任务，不建立隐藏的无限等待队列。

### 结果交付与等待

子任务结束后，父 Agent 自动收到对应任务的结果或失败原因。多个结果同时准备好时可以一并处理，先完成的结果无需等待其他无关子任务。

父 Agent 正在生成回复或执行其他工具时，在当前步骤结束后的可继续执行位置处理新结果。首期不强行打断正在执行的模型请求或普通工具。

没有独立工作可做时，父 Agent 进入等待。等待期间不通过重复询问状态产生模型调用；子任务完成、用户追加消息或停止操作可以结束等待。

多个结果或追加消息同时到达时，父 Agent 合并处理已到达的信息，同一父任务始终只有一条继续执行的流程。停止整个任务优先于继续执行。

每个子任务的终态结果只交付一次。页面重连或重复收到展示更新不会让父 Agent 再次执行同一份结果引出的操作。

“子任务已完成”表示其结果已经产出；父任务仍可能正在检查和整合结果。父 Agent 的最终回答负责区分已验证结论、子任务报告及仍未完成的部分。

### 用户追加消息

用户继续在主会话输入框追加要求。父 Agent 在下一次可继续执行的位置处理；父 Agent 处于等待子任务状态时，追加消息可以唤醒它。

父 Agent 根据新的要求决定继续等待、停止无关子任务，或重新委派。首期子任务说明在启动后固定；需要改变方向时停止原任务并创建新任务。

子任务不提供独立聊天输入框，也不自动接收父会话的全部历史或追加消息。

### 状态展示与用户操作

复用当前子任务列表及抽屉，在主任务进行期间持续展示子任务入口。父 Agent 正在工作或等待时，用户都能查看各子任务。

每个子任务展示标题、当前状态，展开后查看已有执行过程、最终结果或失败原因以及已统计的用量。

| 状态 | 含义 | 用户操作 |
| --- | --- | --- |
| 执行中 | 子 Agent 正在推进任务 | 查看、停止子任务 |
| 等待确认 | 子任务有待处理的工具审批或文件授权 | 查看、处理确认、停止子任务 |
| 正在停止 | 已收到停止请求，正在结束执行 | 查看 |
| 已完成 | 子任务正常结束并产出回答 | 查看结果 |
| 已结束，达到执行上限 | 子任务交付现有进展，仍可能有未完成内容 | 查看交接内容 |
| 失败 | 子任务因错误结束 | 查看原因 |
| 已停止 | 用户或父 Agent 停止该子任务 | 查看已记录的进展及停止原因 |

主任务在没有独立工作可做且仍有子任务未结束时展示“等待子任务”。若其中有待审批操作，同时明确提示用户需要确认，避免把审批等待显示成无原因的停滞。

停止单个子任务只影响该子任务，父 Agent 和其他子任务继续执行。接受停止请求后，该子任务的待审批项立即失效，迟到的审批响应不能恢复执行；其他任务的审批保持可用。正在停止的任务在执行实际结束前继续占用名额，不能提前视为收尾完成。

沿用主任务的“停止”入口，停止整个父任务及其全部活跃子任务。

### 审批与工作范围

子任务继续继承父任务的项目和执行模式，所有工具仍走现有权限规则。需要用户确认时，待办明确标识来自哪个子任务；拒绝后按现有工具失败规则处理。

一个子任务等待确认时，父 Agent 和其他子任务可以继续独立工作。父 Agent 已经依赖该结果且没有其他工作时进入等待。

首期沿用共享项目工作目录。父 Agent 应把只读调查或写入范围不重叠的工作并行委派；存在相同文件的写入依赖时按顺序执行。自动工作区隔离、文件锁和冲突合并不在首期范围内。

### 父任务结束规则

正常结束前，父 Agent 必须处理已经返回的结果；仍需使用的子任务继续等待，已经不再需要的子任务明确停止。所有所属子任务进入终态后，父任务才输出最终回答并标记结束。

阶段性进展继续作为运行中的说明展示。存在尚未收齐的必要结果时，应用保持任务进行中。

| 情况 | 收尾行为 |
| --- | --- |
| 子任务完成 | 父 Agent 接收结果，按任务依赖继续工作 |
| 单个子任务失败或被停止 | 父 Agent 收到原因，决定自行完成、重新委派或说明缺口；其他子任务继续 |
| 父 Agent 判断某个子任务已无必要 | 停止该子任务，保留停止原因，不把它记为成功完成 |
| 用户停止整个任务 | 停止父 Agent 及全部活跃子任务，清理待处理确认；界面完成收尾后显示已停止 |
| 父任务失败或达到执行上限 | 停止剩余子任务，子任务显示“已停止”并注明父任务结束原因，保留已有结果；若能够输出交接说明，明确已完成与未完成内容 |

停止操作阻止后续执行；此前已经完成的文件修改或远端操作保留，不承诺回滚。

首期每个子任务沿用现有最多 128 个模型步骤的限制。达到上限即进入“已结束，达到执行上限”终态，释放活跃名额，并向父 Agent 交付一次进展。父 Agent 不能将交接内容直接当作全部任务已经完成。

### 页面离开、历史与用量

关闭页面、切换会话或刷新浏览器时，父任务及所属子任务继续在当前服务进程中执行。返回运行中的会话后，可以查看子任务状态、结果和待处理确认。

已经结束的子任务保留标题、终态、最终回答或失败原因，以及可取得的用量；父任务结束后刷新页面仍可查看。完整逐步轨迹的历史恢复继续沿用现有边界。

子任务消耗计入所属父任务和会话的总用量，包含失败、停止和重新委派前已经产生的模型调用；同一调用不重复记账，缺失的用量不当作零。

服务进程停止后不恢复执行。重启后保留已保存的子任务终态和结果，父任务显示失败并注明“服务中断，任务未恢复”。尚未保存的子任务过程不保证恢复为独立条目，界面不得将中断前的状态继续显示为执行中。

## 首期范围与保持不变

首期交付父任务与子任务并行推进、结果自动交付、等待与唤醒、子任务状态查看、单独停止和统一收尾。

以下行为保持不变：

- 一个会话同时只有一个活跃父任务；子任务归属于发起它的父任务。
- 子 Agent 使用独立上下文，与父任务共享项目、模型及权限边界。
- 子 Agent 不能继续创建下一层子 Agent。
- 工具审批、文件访问边界及普通工具自身的执行语义沿用现有规则。

首期不包含跨父任务常驻、父任务结束后继续执行、定时运行、服务重启恢复、多层子 Agent、子任务独立聊天、自动文件合并或通用工作流编排。

本功能的成本目标是消除重复状态查询，整体 token 节省比例不作预先承诺。

## 验收标准

1. 委派一个耗时子任务后，在它结束前，父 Agent 能完成一个独立的实际工作步骤；用执行顺序确认并行成立。
2. 同时存在多个子任务时，父 Agent 能利用先返回的结果继续推进，无需等待无关子任务。
3. 父 Agent 无独立工作时进入等待，期间没有反复查询子任务状态的模型调用；结果到达后自动继续。
4. 等待子任务时用户追加消息，父 Agent 能处理新要求；已经执行中的普通工具保持现有执行边界。
5. 某个子任务等待审批时，其他独立工作继续；待审批项能明确对应到子任务，允许和拒绝都可正常收尾。
6. 同一父任务最多 5 个活跃子任务，跨多次委派也不能绕过上限；达到上限有明确反馈。
7. 停止单个子任务后其他任务继续，该子任务的审批立即失效，迟到的审批不能恢复执行；停止整个任务后全部子任务结束，待审批项不再可操作。
8. 子任务失败、停止或达到步骤上限时，父 Agent 获得准确结果，最终回答明确未完成部分。
9. 父任务正常结束时没有仍在执行的所属子任务；已经返回的必要结果被纳入处理，同一终态结果不会重复触发工作。
10. 页面断线、切换会话及刷新不会停止后台执行；返回后可以看到状态和待处理确认。父任务结束后仍能查看已保存的子任务结果。
11. 父任务与会话用量包含所有子任务已统计消耗，失败和停止的任务不遗漏，同一调用不重复累计。
12. 服务重启后任务不自动恢复，父任务明确显示服务中断，已保存的子任务结果可查看，界面不存在虚假的执行中状态。
13. 使用可重复的独立调查任务与原同步等待方式对照，记录答案质量、总耗时、模型调用次数和 token 用量；结论以实测为准。
